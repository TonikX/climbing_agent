## Найденные проблемы

### 1. Максимумы достижения верха и чистого пролаза завышаются

`backend/app/tool_service.py`, `_summary` / `session_max`:
для группы с успешной попыткой берутся категории всех её попыток.
Пример: в одной `route_session_key` есть чистая 6A и неудачная 7A.
Результат: `maxReachedTopGrade=7A`, `maxCompletedGrade=7A` вместо 6A.
`maxAttemptedGrade=7A` при этом корректен. Рекорды вычисляются по успешным
попыткам и могут противоречить общей сводке на такой истории.

Нужно брать максимум категорий только попыток с соответствующим результатом,
не переносить результат между разными историческими категориями одной группы.
В старой документации описана текущая агрегация по сессиям; это объясняет
реализацию, но не соответствует пользовательскому смыслу «максимум чисто».

Воспроизведение: `test_clean_and_top_maxima_use_only_attempts_with_that_outcome`.

### 2. Нет общей нормализации категорий

`_grade_rank` распознаёт только латинские A/B/C: `6С+` с кириллической С
получает иной ранг, чем `6C+`. `_grade_breakdown` создаёт отдельные группы
для `6A`, `6a`, `6а`. `_filter_statistics_rows` не сопоставляет кириллическое
`6а` с сохранённым латинским `6A`, поэтому фильтр возвращает ноль попыток.

Нужна одна функция нормализации для сравнения, группировки и фильтров,
с сохранением исторического значения в snapshot. Составные категории должны
сохранять порядок `6B < 6B/6B+ < 6B+ < 6C`.

Воспроизведение:

- `test_cyrillic_grade_letters_have_same_rank_as_latin`;
- `test_equivalent_grade_spellings_share_one_breakdown_bucket`;
- `test_grade_filter_accepts_cyrillic_equivalent`.

### 3. Python-бот не отображает часть рассчитанной статистики

`backend/app/telegram_format.py`, `statistics` / `summary` не выводят
`durationMinutes`, `completionRate`, показатели попыток на трассу/чистый пролаз,
`previousPeriod` и `comparison`. Эти значения есть в DTO и в старом
TypeScript formatter, но теряются в новом пользовательском интерфейсе.

Воспроизведение: `test_formatter_shows_duration_efficiency_and_comparison`.

## Объём проверки

Новая контрольная история включает предыдущий месяц, текущую неделю,
завершённые и активную тренировки, пустую тренировку, полностью тестовую,
смешанную тренировку, другого пользователя, повторные попытки одной трассы,
все виды страховки и несколько стилей.

Проверены текущая/последняя тренировки, полный список попыток, неделя, месяц,
категории, локации, проекты, рекорды и прогресс. Счётчики сверены с рассчитанными
вручную значениями. Проверены включительные границы дат, високосный февраль,
переход года, пустые выборки, неверные даты, фильтры и сравнение периодов.
Существующие тесты дополнительно проверяют срывы/зависания, исправления
результатов, RLS, авторизацию и независимость исторической категории от каталога.

Проверен путь Telegram callback → сервис → DTO → formatter → очередь сообщений:
кнопки не создают AI jobs; свободный запрос использует одну AI job для intent,
без дополнительного задания на форматирование. Внешняя модель и реальная
отправка Telegram в этих тестах не вызываются. Длинные ответы проверяются
с учётом разбиения на сообщения.

Трассы и проекты по текущему контракту считаются по `route_session_key`.
Это группы попыток, а не уникальные маршруты каталога за всю историю.
Успешный пролаз в другой группе автоматически не закрывает прежний проект.
Это отдельное продуктовое правило, не изменённое в ходе проверки.

## Повторный запуск

На отдельной тестовой PostgreSQL, с переменными `DB_HOST`, `DB_NAME`, `DB_USER`,
`DB_PASSWORD`, `INTERNAL_API_KEY=test-auth-key` и установленными зависимостями:

```sh
cd backend
PYTHONPATH=. pytest -q -p no:cacheprovider tests
```

Для старого TypeScript-интерфейса: `npm test` и `npm run build`.
Регрессионные проверки найденных дефектов оставлены без `skip`/`xfail`:
до исправления реализации они должны падать. В рамках этого задания добавлены
тесты и отчёт; логика приложения не исправлялась и не развёртывалась.
