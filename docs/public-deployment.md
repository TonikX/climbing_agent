# Многопользовательский сервис: 1.0.0-beta.1

Код подготовлен для закрытой проверки на отдельном Telegram-боте и отдельной БД.
Это ещё не подтверждение готовности к нагрузке 10 000 пользователей / 1 000 DAU.
Действующий бот, его webhook и данные при разработке не переключались.
Старые `compose.yaml`, `scripts/deploy.sh` и инструкция OpenClaw относятся к
предыдущему стеку; не используйте их для запуска этой версии.

## Что реализовано

- Собственный aiogram/webhook-адаптер, FastAPI, PostgreSQL и Nginx. OpenClaw
  отсутствует в публичном тракте.
- Автоматическая регистрация `pending_approval`, заявка в личный чат владельца,
  одноразовые «Одобрить / Отклонить», блокировка администратором. Проверяются
  identity отправителя, личный чат и исходная доставленная карточка заявки.
  Пользователь никогда не получает права администратора только потому, что он первый.
- Отдельные очереди команд, AI и доставки. Updates, jobs и outbox сохраняются
  атомарно; повторные updates не создают повторных записей. Lease, heartbeat,
  ограниченные повторы, последовательность изменений одного пользователя.
  Доставка в Telegram имеет семантику at-least-once: при потере ответа Telegram
  после фактической доставки возможен повтор сообщения.
- PostgreSQL FORCE RLS на таблицах, отдельные роли миграции, API и control.
  Личные каталоги наследуют владельца района; публичный каталог только для чтения.
  Входящие tools не доступны в публичном режиме.
- Типизированный HTTP API: тренировки/попытки, каталог, снаряжение, профиль,
  тестовый режим, статистика, экспорт и подтверждённое удаление. Пагинация,
  `Idempotency-Key`, проверки владельца и `expected_version` для PATCH.
- Кнопки статистики и ручной ввод без LLM. Свободный текст — один вызов для
  определения intent, затем общий сервис статистики и formatter. Голос —
  Whisper в Cloud.ru, затем один DeepSeek. Форматирование не вызывает LLM.
- Ручная форма учитывает style, belay, достижение верха, чистоту, срывы и зависания.
  Срыв/зависание исключают чистый пролаз. Тестовые записи исключены из статистики.
- Лимиты AI/аудио, резервирование общего бюджета, прекращение устаревшего задания
  после отмены/смены тренировки. По умолчанию платные запросы отключены.
- Экспорт, удаление личных данных, журнал удалений для восстановления резервных
  копий, очистка очередей, readiness и административные метрики.

## Настройка тестового окружения

Скопируйте `.env.public.example` в `.env.public`, заполните разные случайные
пароли миграции/runtime/control и `INTERNAL_API_KEY` длиной не меньше 32 символов.
Файл секретов игнорируется Git. Нужны отдельный тестовый бот, числовой
`TELEGRAM_BOT_ID`, подтверждённый числовой `ACCESS_APPROVER_TELEGRAM_ID` и
`ACCESS_APPROVAL_CHAT_ID`, равный ID владельца для личного чата. Старый allowlist
не определяет владельца. Подставьте TLS-сертификат, приватный ключ и HTTPS URL.
Порты по умолчанию 8080/8443; для отдельного публичного домена настройте 80/443
или внешний TLS-прокси. База опубликована только на loopback для SSH-туннеля.

Для пустой тестовой БД первый запуск выполняется явно:

```sh
docker compose --env-file .env.public -f compose.public.yaml config --quiet
docker compose --env-file .env.public -f compose.public.yaml build
docker compose --env-file .env.public -f compose.public.yaml up -d postgres
docker compose --env-file .env.public -f compose.public.yaml run --rm migrate python -m app.migrate_public --schema-only
docker compose --env-file .env.public -f compose.public.yaml run --rm migrate python -m app.operator_setup
docker compose --env-file .env.public -f compose.public.yaml up -d
```

`operator_setup` активирует только явно настроенного владельца. Миграции
выполняются отдельным процессом; API/worker не запускают Alembic. `/ready`
проверяет безопасные роли, FORCE RLS и активированного администратора.

Webhook задаётся отдельной командой после готовности HTTPS:

```sh
docker compose --env-file .env.public -f compose.public.yaml run --rm --no-deps worker-ai python -m app.webhook_setup
```

Нужен случайный `TELEGRAM_WEBHOOK_SECRET` длиной минимум 32 символа. Команда
проверяет соответствие токена ID бота, не удаляет накопленные updates. Выполнять
её с токеном рабочего бота можно только в согласованное окно переключения,
после остановки старого polling/OpenClaw. Для этой задачи webhook не менялся.

AI настраивается через `CLOUDRU_API_KEY`, `CLOUDRU_MODEL` и `CLOUDRU_ASR_MODEL`.
Доступность выбранной модели проверяется отдельно на аккаунте Cloud.ru.
`AI_DAILY_BUDGET_UNITS` — дневной бюджет в копейках;
`AI_CALL_RESERVATION_UNITS` — верхняя оценка стоимости одного вызова с учётом
ограниченного входа и ответа. Голос резервирует два вызова. Без положительного
бюджета и резерва работают кнопки и ручная форма, платный AI не запускается.
Счётчики токенов сохраняются; точное списание по тарифу провайдера и сверка
с биллингом пока не реализованы, используется консервативный резерв.

## Перенос существующих данных

Сначала сделайте резервную копию и репетицию на восстановленной отдельной БД.
В `PUBLIC_MIGRATION_MANIFEST` задайте JSON с проверенными `approved_user_ids`
и `location_owners` (все существующие ID районов → ID владельцев). Без полного
решения миграция остановится. Остальные аккаунты становятся `pending_approval`, ранее
заблокированные остаются `blocked`, старые auth-сессии отзываются.

Район, на который ссылаются тренировки нескольких пользователей, нельзя
автоматически назначить одному. До миграции подготовьте проверенные личные
копии его иерархии и перепривяжите соответствующие тренировки/сектора/попытки
в восстановленной БД. Исторические route snapshots не изменяйте. Сверьте
количество тренировок, попыток, даты, стиль, страховку и тестовые отметки для
каждого владельца. Миграция проверяет межпользовательские ссылки и прерывается
при неоднозначности; общего автоматического клонирования каталога пока нет.

## Проверка API и бота

OpenAPI: `/api/v1/docs`. Публичные операции требуют Bearer-сессии; Telegram login
является внутренней доверенной операцией, клиент не может выбрать произвольный
user ID. `/api/v1/internal/*` закрыты Nginx и требуют служебный ключ.
Административные метрики: `GET /api/v1/admin/metrics` с Bearer администратора.

Проверьте два разных аккаунта: заявку, повторную заявку, отказ, одобрение,
чужие ID, блокировку, создание тренировки, ручную попытку, текст и голос,
статистику, экспорт и удаление. До одобрения журнал/статистика/платные вызовы
недоступны. Если AI-сообщение ещё обрабатывается, завершение тренировки предлагает
подождать или отменить его; REST finish возвращает 409 до явного
`cancel_pending=true`. Поздний ответ не записывается в следующую тренировку.

Тесты используют PostgreSQL и отдельные схемы; не запускайте их на рабочей БД.

```sh
cd backend
PYTHONPATH=.:tests python -m pytest tests -q -p no:cacheprovider
```

Для нагрузки предусмотрен `python -m app.load_test`: `--seed` разрешён только
в пустой БД с именем `*_load_test` и `CONFIRM_ISOLATED_LOAD_TEST=yes`, под ролью
миграции. Fixture: 10 000 пользователей, 100 000 тренировок, 1 000 000 попыток,
100 синтетических сессий. После seeding запускайте API с обычными runtime/control
ролями, затем `python -m app.load_test --url https://TEST_HOST --seconds 1800 --rps 20`.
Скрипт проверяет смесь чтений и PATCH, 100 клиентов, отсутствие ошибок и p95 ≤500 мс.
Он не заменяет проверку burst 50 Telegram updates/с в течение 60 секунд, fairness,
сбоев worker/Telegram/провайдера и p95 полного пользовательского сценария.

## Резервные копии и восстановление

`scripts/backup-public.sh` запускайте ежедневно системным таймером. Нужны `age`,
`rsync`, `PUBLIC_BACKUP_AGE_RECIPIENT`, отдельный удалённый
`PUBLIC_BACKUP_SSH_TARGET`; доступы задаёт оператор. Скрипт шифрует pg_dump и
журнал удалений, отправляет их на другой сервер и отмечает успешную отправку.
Настройте срок хранения локальных/удалённых копий 30 дней и оповещение об
отсутствии успешной копии более 24 часов. Таймер/удалённое хранилище автоматически
не устанавливаются этой версией.

Журнал удалений необходимо независимо и регулярно реплицировать вне БД;
ежедневная копия рядом с dump недостаточна для удалений после последнего backup.
Экспорт: `python -m app.deletion_ledger --export` (control-role). Перед запуском
восстановленного API расшифруйте **самый свежий независимый** журнал и выполните
`python -m app.deletion_ledger --replay /PATH/latest-ledger.json`, задав
`DB_CONTROL_USER`/`DB_CONTROL_PASSWORD` роли миграции для этой одноразовой команды.
Затем верните обычные роли. Не сохраняйте привилегированные credentials в API.
Проверяйте отсутствие удалённых аккаунтов и их каталога, истечение старых сессий,
отсутствие повторной отправки старого outbox; перед возобновлением доставки
проведите ревизию восстановленных очередей.

## Что остаётся перед публичным запуском

- Подтвердить ID владельца, отдельного бота, домен/TLS и стоимость/бюджет AI.
- Пройти перенос на копии реальных данных, включая неоднозначные общие каталоги.
- Провести полный нагрузочный тест и тесты отказов по критериям ТЗ.
- Подключить независимое хранилище журнала удалений, off-site backup, таймеры,
  оповещения и выполнить реальное восстановление с проверкой RPO 24ч / RTO 4ч.
- Проверить текст/голос на реальном тестовом боте и закрытую бету.

Импорт AllClimb не является условием работы личного журнала и не включён в
публичный rollout. Его отдельный статус описан в `docs/allclimb-import.md`.
